# Security model

This document states what the app protects, how, and — just as importantly —
what it does **not** protect against. No application can honestly promise that
every forensic technique or every compromised device can be defeated. The goal
here is concrete and bounded:

> Possessing the phone, or copying the app's storage, should not by itself yield
> readable private records. The database holds ciphertext; the keys to read it
> are derived from a passphrase that is never stored.

## Architecture

### Two vaults, two keys

The app has two independent workspaces — a **Finance** vault and a **Private**
vault. They are not merely different screens: each has its own encryption key.

```
passphrase ──Argon2id(salt, 64MiB, t=3)──▶ KEK ──unwraps──▶ DEK ──AES-256-GCM──▶ records
   (never stored)                          (transient)       (random, wrapped)
```

- Each vault has a random **data-encryption key (DEK)**, 256 bits, generated by
  the CSPRNG at vault creation. The DEK — not the passphrase — encrypts records.
- The passphrase is stretched with **Argon2id** (memory-hard, 64 MiB default)
  using a per-vault random salt to produce a **key-encryption key (KEK)**.
- The DEK is stored **wrapped** (encrypted) under the KEK with AES-256-GCM. The
  raw DEK is never written to disk.
- Unlocking derives the KEK from the entered passphrase and tries to unwrap each
  vault's DEK. The passphrase that successfully unwraps a vault's DEK opens that
  vault. **Unlocking one vault gives no ability to read the other**, because the
  other vault's DEK is wrapped under a different, independently-derived key.

The passphrase is never used directly as the record key, is never stored, and
is not recoverable. A wrong passphrase is indistinguishable from a tampered
wrap: GCM's authentication simply fails.

### Authenticated encryption

All records and backups use **AES-256-GCM** with a fresh random 96-bit IV per
message. GCM is authenticated: any modification to the ciphertext, IV, or
associated data makes decryption fail. Each record is bound to its identity
(`vault:collection:id`) via GCM associated data, so a stored ciphertext cannot
be silently relocated to a different record slot (a cut-and-paste / swap attack).

### Storage

Records live in **IndexedDB**. Each row stores only:

- `id`, `vault` (which key decrypts it), `collection` (a coarse type tag), and
- `payload`: the AES-256-GCM ciphertext.

No names, amounts, dates, notes, or totals are stored in the clear. Totals are
always recomputed from decrypted records at runtime, never persisted.

### Key handling in memory

- The live DEK is a **non-extractable `CryptoKey`**. The browser will not export
  its raw bytes back to JavaScript, limiting exposure even within the running
  page.
- Transient key material (the passphrase's UTF-8 bytes, the derived KEK, the
  unwrapped DEK bytes) is zeroed (`wipe()`) immediately after use.
- On lock, the DEK reference is dropped so the vault becomes unreadable until the
  passphrase is re-entered.

JavaScript cannot guarantee that the GC never copied a buffer, so this is
best-effort defense-in-depth, not a hard guarantee (see Limitations).

## Automatic locking

| Trigger | Behavior |
| --- | --- |
| App sent to background / task-switched | Private vault locks (configurable); a privacy shield covers content so the OS switcher snapshot shows nothing |
| Inactivity timeout | Vault locks (configurable, default 120s) |
| External device connection | Best-effort lock on WebUSB `connect` (see Limitations) |
| Failed authentication | Rate limited with escalating backoff (5s → 15m) after 5 attempts |
| Manual "Lock now" | Immediate lock |

A connected computer **locks** the vault and protects the keys — it never
destroys data. An external computer is treated as untrusted, but accidental data
loss is avoided.

## Backups and export

- **Encrypted backups** are double-sealed: records are already ciphertext under
  the vault DEK, and the whole bundle is sealed **again** under a *separate*
  backup key derived (Argon2id) from a distinct backup passphrase. A backup is
  never a plaintext copy. Restoring re-installs the encrypted vault, which the
  original vault passphrase then opens.
- **Exports** are controlled and scoped to the unlocked vault:
  - *Full* — complete authorized records (JSON).
  - *Finance* — financial rows without notes/personal detail (CSV).
  - *Summary* — totals only.
  - *Anonymized* — names replaced with random identifiers, free-text stripped.
  Because a finance export is built only from finance-vault data (the code has no
  access to the private DEK while in the finance vault), private records cannot
  leak into a finance export. That separation is structural, not a checkbox.

## Threat model

**Defends against:**

- Theft of the device or a copy of its storage (disk image, IndexedDB dump,
  backup file) **while the vault is locked**. The attacker sees ciphertext and a
  wrapped key, and must brute-force an Argon2id-stretched passphrase offline.
- Tampering with the stored database — authenticated encryption makes silent
  modification detectable.
- Accidental leakage of private data into ordinary finance exports.
- Casual inspection via the app UI (nothing readable without the passphrase).

**Explicitly out of scope / limitations:**

- **Passphrase strength is the ceiling.** A weak passphrase can be brute-forced
  offline regardless of Argon2id. Use a long, unique passphrase per vault.
- **A compromised device while unlocked.** Malware, a screen-recorder, or an
  attacker with the vault open can read decrypted data. Auto-lock shortens but
  cannot eliminate this window.
- **No hardware-backed keystore in this build.** As a web PWA, keys are protected
  by the passphrase + the browser/OS storage sandbox, **not** by a Secure Enclave
  or StrongBox. A native build (iOS Keychain/Secure Enclave, Android
  Keystore/StrongBox) is the intended path to hardware-bound, biometric-gated
  keys and is described in the README roadmap. Do not assume hardware key
  isolation here.
- **"External computer" detection is best-effort.** The web platform has no
  reliable "USB/forensic cable attached" signal; the WebUSB `connect` heuristic
  and background/blur locking are approximations. A native build can observe
  USB/MTP state directly.
- **Existence of the private vault is not hidden.** Vault metadata reveals that a
  second vault exists. This design provides *separate keys*, not *plausible
  deniability of existence*; a hidden-volume design would be required for the
  latter.
- **Memory scraping.** JavaScript cannot guarantee prompt, complete erasure of
  key material from process memory.
- **Remote wipe / device revocation** is a roadmap item; this local-only build
  cannot remotely destroy or revoke a lost device's data.

## Phase 5 — security testing checklist

These are the properties to test; items marked ✓ have automated coverage in
`tests/`.

- ✓ **Database extraction** — records persisted are ciphertext only; a wrong key
  yields no plaintext (`vault.test.ts`, `crypto.test.ts`).
- ✓ **Vault isolation** — a record sealed under one vault's key cannot be opened
  with the other's (`vault.test.ts`).
- ✓ **Authentication bypass** — unlock succeeds only with the correct passphrase;
  colliding passphrases across vaults are refused (`vault.test.ts`).
- ✓ **Tamper detection** — flipped ciphertext / wrong AAD is rejected
  (`crypto.test.ts`).
- ✓ **Backup exposure** — backup file contains no plaintext; wrong backup
  passphrase fails; round-trip restores (`backup.test.ts`).
- ✓ **Rate limiting** — repeated failures trigger escalating lockout
  (`vault.test.ts`).
- ✓ **End-to-end** — real-browser flow incl. separate-key routing
  (`scripts/smoke.mjs`).
- ☐ **Key leakage / memory exposure** — audit that raw DEK/KEK bytes are wiped
  and never logged (manual; `wipe()` in place, needs heap-snapshot review).
- ☐ **Logging leaks** — confirm no sensitive values reach console/notifications
  (minimal-logging by design; needs a lint/grep gate).
- ☐ **Export scoping** — verify no cross-vault data in scoped exports (structural
  guarantee; add an explicit test).
- ☐ **Device theft** — manual: image storage while locked, confirm unreadable.

## Reporting

This is a demonstration build. If adopting it, commission an independent review
of the crypto integration and the native key-storage layer before trusting it
with data whose exposure would cause real harm.
